I configured file integrity monitoring and the event streams that surface anomalies, on this host, for this case.

Payload locations. I watch C:\Users\*\AppData\Roaming because iblenor.exe was written there under my own user's profile, so the next drop will land in whichever profile is logged on. I watch C:\Users\*\AppData\Local\Temp because droppers stage there between download and execution and nothing legitimate persists in it. I watch C:\Users\*\Downloads because the lure PORTWAY-DISPATCH-UPDATE.js ran from there at 07:55:00, which is how this intrusion entered. I watch C:\Users\Public and C:\ProgramData because both are writable without a profile and are the shared staging an attacker uses when a user folder is being watched, and because the Northmoor deploy agent also uses ProgramData, any change there must be attributable to a package such as pkg_7708.

Persistence surfaces. I watch both Startup folders, per-user and all-users, because that is the same autostart primitive as the Run key and needs no privilege. I watch C:\Windows\System32\Tasks because seven scheduled tasks already predate the incident window, so an addition or an edit is the change that matters. I watch HKCU and HKLM Software\Microsoft\Windows\CurrentVersion\Run and RunOnce, and the wildcard HKEY_USERS\*\...\Run, because Tavistock9 -> AppData\Roaming\iblenor.exe was written to that key at 07:55:14.051 and a write in any loaded hive has to be visible.

Anomaly checks. I enabled Sysmon EID 1 with command line because both powershell.exe processes in this case share the image and MD5 121E1253E10DBE8D2D06AAE33EDBC859, so only the parent image and the command line separate the lure chain from the deployment chain. I enabled EID 11 with hashes so a dropped binary is pinned to the ProcessGuid that wrote it, EID 13 because the Run value exists in no other stream, and EID 3 with destination hostname because the two chains differ by where they talked, 198.51.100.47 externally against 10.42.8.0/24 internally, which is exactly what decided pkg_7714. I enabled the Windows audit policy for process creation with command line so the trail outlives the agent or the re-image.

What I did not enable, on purpose. I did not watch the whole disk, C:\Windows\WinSxS, SoftwareDistribution, servicing, the pagefile or the system hive: they change on every patch cycle, they would bury the Tavistock9 signal in update noise, and integrity there belongs to patch management. That leaves a scope of nine paths, four registry locations and five event checks, each one a place this incident used or would have used, which is the whole point of not watching everything.
