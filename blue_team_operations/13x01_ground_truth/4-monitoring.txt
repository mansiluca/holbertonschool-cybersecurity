## Configuration delivered to PORTWAY-WS-114

```xml

  <!-- frequency: watch for new files, not just changes -->
  <disabled>no</disabled>
  <frequency>300</frequency>

  <!-- user-writable locations where a payload can land or a lure can sit -->
  <directories check_all="yes" realtime="yes" report_changes="yes">C:\Users\sdumont\AppData\Roaming</directories>
  <directories check_all="yes" realtime="yes" report_changes="yes">C:\Users\sdumont\AppData\Local\Temp</directories>
  <directories check_all="yes" realtime="yes" report_changes="yes">C:\Users\sdumont\Downloads</directories>
```

```xml
<localfile>
```

Sysmon events that must be enabled on the endpoint for those streams to mean
anything: EID 1 with command line, EID 11 with hashes, EID 13 and EID 3 with
destination hostname.

## Why each one is watched, for this case

| location or check | why, tied to this incident |
|---|---|
| `AppData\Roaming` | iblenor.exe was written here (EID 11) and the Run key pointed back at it; a new executable under this tree is the same move |
| `AppData\Local\Temp` | staging for droppers between download and execution; nothing legitimate on a dispatch workstation persists here |
| `Downloads` | the lure `PORTWAY-DISPATCH-UPDATE.js` was executed from here at 07:55:00, so a new script here is how the next case starts |
| `Users\Public` | writable with no profile; the shared drop used when the user's own AppData is being watched |
| `ProgramData` | writable staging shared by the Northmoor deploy agent and by attackers, so a change here must be attributable to a package like `pkg_7708` |
| both `Startup` folders | the autostart primitive that replaces a Run key, per-user and all-users |
| `System32\Tasks` | scheduled-task store; seven tasks already predate the incident window, so additions are the change worth seeing |
| three Run keys | `Tavistock9 -> AppData\Roaming\iblenor.exe` was the persistence actually used; RunOnce is where a second stage gets staged; the HKEY_USERS wildcard makes a write in any loaded hive visible |
| Sysmon EID 1 | the two `powershell.exe` in this case share image and MD5 `121E1253E10DBE8D2D06AAE33EDBC859`; only parent image and command line separate the lure chain from the deployment chain |
| Sysmon EID 11 | iblenor.exe is evidence because its hash is pinned to the ProcessGuid that wrote it, not because of its name |
| Sysmon EID 13 | the `Tavistock9` value exists only in this stream; file monitoring alone would have missed the persistence |
| Sysmon EID 3 | the two chains differ by destination: `198.51.100.47` external versus `10.42.8.0/24` internal, and `pkg_7714` was decided on that single connection |
| Windows audit policy, process creation with command line | so the trail survives the agent being uninstalled or the host being re-imaged |

## Scope, and what is deliberately left out

Twelve watched objects: five payload directories, three persistence paths, three
Run-key families and one scheduled-task store, plus five event/audit checks. Every
one is a place this incident used or would have used.

Not watched: the whole disk, `C:\Windows\System32`, `C:\Program Files` and the
system hive. They change on every patch cycle, would bury the `Tavistock9` signal
in update noise, and integrity there belongs to patch management. Watching
everything is not a decision, and an analyst who cannot say why a path is
monitored has not made one.
