DIR C:\Users\sdumont\AppData\Roaming - WHY: user-writable profile path where iblenor.exe was dropped (EID 11); a new executable here is this case's signature
DIR C:\Users\sdumont\AppData\Local\Temp - WHY: user-writable staging where droppers unpack before moving; nothing legitimate persists here
DIR C:\Users\sdumont\Downloads - WHY: arrival point of the lure PORTWAY-DISPATCH-UPDATE.js, which was executed from here (EID 1)
DIR C:\Users\Public - WHY: writable by any local user with no profile; shared drop location used when the user's own directory is watched
DIR C:\ProgramData - WHY: broadly writable staging shared by deployment tooling and attackers; changes here must be attributable to a package
DIR C:\Users\sdumont\AppData\Roaming\Microsoft\Windows\Start Menu\Programs\Startup - WHY: per-user autostart, runs at logon with no privilege
DIR C:\ProgramData\Microsoft\Windows\Start Menu\Programs\Startup - WHY: all-users autostart, same primitive with a wider blast radius
DIR C:\Windows\System32\Tasks - WHY: scheduled-task store, persistence surviving reboot without a service account
KEY HKLM\Software\Microsoft\Windows\CurrentVersion\Run - WHY: machine-wide autorun, the strongest Run-key primitive on the host
KEY HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce - WHY: machine-wide one-shot autorun, typical staging of a second stage
KEY HKCU\Software\Microsoft\Windows\CurrentVersion\Run - WHY: per-user autorun; the intrusion wrote Tavistock9 here pointing at iblenor.exe, so this key is mandatory
KEY HKEY_USERS\*\Software\Microsoft\Windows\CurrentVersion\Run - WHY: same key family across every loaded hive, so a write in any profile is seen
CHECK Sysmon EID 1 process creation with command line - WHY: lineage is decided by parent image and command line; without them powershell.exe looks identical on both chains
CHECK Sysmon EID 11 file creation with hashes - WHY: a dropped binary is evidence only if its hash is pinned to the ProcessGuid that wrote it
CHECK Sysmon EID 13 registry value set - WHY: autorun persistence is a registry value and no other stream shows it being set
CHECK Sysmon EID 3 network connection with destination hostname - WHY: the C2 is identified by where a process talked, not by its name
CHECK Windows audit policy, process creation with command line - WHY: so the trail survives the agent being uninstalled or the host re-imaged
PERSISTENCE SURFACES COVERED: HKCU and HKLM Run and RunOnce keys, every loaded user hive's Run key, both Startup folders and the scheduled-task store - the four places this host would have to be touched to survive a reboot
ANOMALY SURFACES COVERED: the four Sysmon streams the verdict depends on (process lineage, file writes with hashes, registry value sets, network connections with destination), plus audit policy so the trail survives an agent change
SCOPE BOUNDARY: whole disk, C:\Windows\System32, C:\Program Files and the system hive are deliberately NOT monitored - they change on every patch cycle, bury the signal and cost the endpoint, so integrity there belongs to patch management
WHY NOT EVERYTHING: eight directories, four Run-key families and four event streams, each one a place this case used or would have used; anything wider would fire on a Windows update and teach the team to ignore the rule
